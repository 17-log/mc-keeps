## 延续当前 8 题 / 4 轴 / 16 角色

当前源码的四条轴如下，每轴两题，每题四个选项。继续完善现有配置，不按研究初稿另建第二套评分，也不重复新增一个人格模块。

| 维度 | 两端 | 角色码 |
| --- | --- | --- |
| 同行方式 | 独享 / 搭子 | D / B |
| 小事仪式 | 随性 / 仪式 | S / Y |
| 口味探索 | 经典 / 探索 | C / T |
| 回忆习惯 | 当下 / 收藏 | X / Z |

选项分值为 `−2、−1、+1、+2`。每轴两题之和加 4，再除以 8，四舍五入到 0–100。小于 50 取左侧代码；大于 50 取右侧代码；50 明确显示“混合偏好”，角色码固定取右侧以稳定展示。不要把刻度改写为概率、科学量表结论或人格优劣。

16 个角色的名称、短句、标签和小任务已在 `persona-engine.js` 配置，包含“晚风独享家”“日常拾光者”“落日收藏家”“相聚纪念官”等。像素矩阵由 `persona-art.js` 维护，页面与 PNG 共用；有八类食物及表情变体，不应包装成十六套完全独立美术。二维码依赖及原创边界见 [第三方声明](../THIRD_PARTY_NOTICES.md)。

## 需要保持完整的分享闭环

1. **自测：**无需登录、传照片或连接 MCP，完成八个日常选择；进度清楚，允许回退和修改。
2. **结果：**显示称号、像素角色、一句话、四轴解释与今日小任务；图鉴预览明确是示例。
3. **分享：**复制版本化结果深链，或导出含相同结果二维码的 1080 × 1440 PNG；支持的浏览器可调用系统分享。
4. **朋友：**打开深链先看到分享者结果，自测后或使用本机上次结果，对照四轴共同点与不同点。只谈生活偏好，不给关系打分。
5. **手帐：**点击任务后打开原编辑器的个人草稿，用户确认实际餐品、日期和照片，再主动「收进日历」。

实际链接形如 `https://17-log.github.io/mc-keeps/#persona?v=p1&r=<结果令牌>`，只带版本、角色码与四条刻度摘要。生成链接和二维码使用配置的公开地址，即使本地体验也如此；公开站必须有兼容构建。链接不带逐题答案、照片或订单，但持有者可查看和继续转发结果摘要，它也不是身份认证凭证。

任务预填不是已发生的消费，不自动关联订单，也不会在用户确认前保存。当前没有多人协同编辑一页、任务完成追踪或自动生成周报，演示与文案不要暗示这些功能已经具备。

## 三条短视频脚本与分享配文

以下是录制方案。先准备真实操作得到的示例结果；用项目画面和自己的拍摄素材，不伪造评论、分享成功或用户数量。功能与公开地址验证后再使用对外体验引导。

### 1. 下班后的快乐，原来也有名字

**15–20 秒：**0–3 秒收起电脑，字幕“下班后，你想独处，还是找个搭子？”；3–8 秒录制两道场景题；8–13 秒揭晓真实测出的“晚风独享家”或其他实际角色，放大一句结果文案；13–20 秒点击小任务进入手帐草稿，字幕“给今天留一页，再测测你的那一面”。不需要额外制作尚未实现的城市冒险页面。

**分享配文：**“原来我是「晚风独享家」。今天想给自己留十分钟，再把这一口写进日历。8 个生活片刻，测测你把日子吃成了哪种浪漫。”角色名称随实际结果替换，附通过验证的结果链接。

### 2. 同一顿饭，两种快乐

**15–20 秒：**0–3 秒两个人点单，一人说“还是老样子”，另一人说“想试新品”；3–9 秒剪辑各自真实的选择与结果；9–15 秒录制从朋友深链进入并完成偏好对照，突出“经典 / 探索”的不同；15–20 秒切到各自手帐，字幕“你负责熟悉，我负责发现；都值得记一笔”。

**分享配文：**“我想吃熟悉的，你想试没吃过的。测完发现，我们记住一顿饭的方式也不同。把你的结果发来，看看哪里同频，哪里可以互相带一带。”不要称为匹配率，也不演成多人共写同一份在线日记。

### 3. 一口变成一页

**15–20 秒：**0–3 秒展示自己的零散餐食照片，字幕“吃过很多，记住了多少？”；3–7 秒展示八题进度与真实结果；7–15 秒点击任务、确认餐品、加照片、写一句、保存到日期；15–20 秒翻开日历中的那一页，字幕“一张照片，一句话，今天也有坐标”。

**分享配文：**“不用写很长的日记。把今天的一口、当时的心情和日期，收成一页。我的像素人格是「日常拾光者」，你呢？”角色名称按实际结果替换。

## 同仓库后续操作

| 顺序 | 操作与交付 |
| --- | --- |
| 1. 阅读现状 | 阅读 [README](../README.md)、[人格说明](personality.md) 与现有源码；沿用 `#persona`、原编辑器、IndexedDB 和构建方式。确认公开版本，避免把已实现内容重复开发 |
| 2. 做小范围改善 | 先处理真实反馈中的答题理解、卡片可读性、手帐确认和手机分享问题；题目、评分、角色文案与像素矩阵分别维护 |
| 3. 保持原流程 | 真实订单继续沿用 [现有 MCP 接入](../MCP_INTEGRATION.md) 的本机只读边界；照片手帐可独立使用，订单需本人确认，不能从人格结果猜消费 |
| 4. 构建与验证 | 按仓库命令操作，修改源文件后再生成单文件；交付实际检查结果，包括结果还原、无效链接回退、PNG 中文与 QR、好友对照、草稿保存与取消、原手帐和 MCP 回归 |
| 5. 公开访问检查 | 按已授权的发布流程继续同一仓库，确认公开 HTTPS 入口、全新浏览器打开结果、真实手机扫码和平台内置浏览器；只有观察到现网更新后才作发布声明 |
| 6. 内容试用 | 使用上面的真实录屏与结果卡观察反馈；记录看不懂、打不开、无法保存等问题，再决定扩展内容 |

这些是后续工作顺序，不是新的测试或部署结果。本交接文档不替代当次验证与发布记录。

## 建议指标：尚未接入埋点

当前人格模块没有分析埋点，以下只是后续建议，**没有相应统计结果**。先说明采集范围、事件口径与去重方式，再决定是否接入。不要把完整答卷、照片、日记正文、订单、Token 或完整结果令牌作为分析参数。

| 事件组 | 用来回答的问题 | 解释限制 |
| --- | --- | --- |
| 测试开始 / 完成 | 八题是否顺畅，哪一步容易退出？ | 不凭访问量推算独立用户 |
| PNG 导出成功 / 链接复制成功 | 有多少人愿意带走结果？ | 操作成功不等于已经分享到社交平台 |
| 结果深链打开 / 接收者完成自测 | 朋友能否接着完成体验？ | 未定义归因与去重前，不计算“传播系数”或真实新增人数 |
| 草稿打开 / 日记确认保存 | 测试是否引导出一页真实记录？ | 预填草稿不等于保存；现有保存事件也不自动等于任务完成 |

若后续确有需要，再考虑次周记录与回访。不能先展示虚构转化率，再补采集实现。

## 后续范围与原创边界

可考虑的下一步包括：用户主动选择记录生成“本周手帐卡”；围绕下班、独处、节日等真实情境更新原创短句、任务和像素场景；更顺畅地结合用户确认后的订单事实与照片。周卡应标明基于几条记录，不把少量记录包装成稳定人格，也不从消费、食物或照片推断疾病或心理状态。

这些是候选扩展，不表示当前已经实现。优先观察现有八题到手帐的路径，再决定是否投入。保留同一个项目的品牌、数据和部署结构，不扩展成另一套人格社交网络。

交付应报告实际修改、真实验证、公开访问状态与剩余问题。参考社媒的表达机制，不复制题库、角色或美术；不承诺传播率，也不以未经核实的“热点”包装更新。
